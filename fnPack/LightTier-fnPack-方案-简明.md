# LightTier 飞牛 fnOS（fpk）方案 · 简明版

> 修订：2026-10-19 v2。上一版把"官方控制台是单设备单节点"列为 F 系的缺陷，**已被上游源码推翻**（详见详细版第十一节）。本版同时移除了因此得出的错误选型判据。完整依据与取证标记见 [`LightTier-fnPack-方案-详细.md`](./LightTier-fnPack-方案-详细.md)。

---

## 先说清楚一件事

LightTier 和官方 web 控制台在架构里**占同一个位置——都是界面，都不参与组网**。真正干组网活的只有 `easytier-core` 一个二进制。

所以所有方案的区别只有一句话：**给 NAS 上的 core 配哪个控制面，以及那个控制面的代码从哪来。**

---

## 决策只有一个开关

> **你要统一的是"观感"，还是"代码"？**

- 统一**观感**（NAS 上长得像 LightTier，但接受 NAS 端是另一套实现）→ **F2**，最省，后端零改动。
- 统一**代码**（桌面/NAS/手机共用一份前端逻辑，少维护一个界面）→ **B+**，代价是要自己写并长期维护内核编排。

两条路都**不是**"LightTier 原版跑在 NAS 上"——桌面版前端的数据语义是"配置文件 → 进程 → 端口"，官方控制台是"用户 → 网络 → 成员 → Gateway"。区别只在于 F2 明确接受重写，B+ 试图复用。

---

## 四条路线

|  | A · 官方控制台原样 | **F2 · 官方后端 + LightTier 风格界面** | B+ · agent 编排 core | F1 · 自编译 web |
| --- | --- | --- | --- | --- |
| 界面 | 官方 PrimeVue 控制台 | **自研，LightTier 观感** | LightTier 原版 dist | 自研，替换 embed |
| 后端二进制 | 官方 | **官方，不动** | 官方 core + cli | **要自己编 Rust+proto** |
| 组网行为由谁负责 | 官方 web+core | 官方 web+core | **你的 agent** | 官方 web+core |
| 配置持久化 | 官方 `et.db` | 官方 `et.db` | agent 自己落盘 | 官方 `et.db` |
| fpk 改动量 | 已完成 | **改 image + 加一个静态服务** | 新建镜像与整套编排 | 同 F2，另加分叉维护 |
| 多网络/多实例 | ✅ 支持 | ✅ 支持 | ✅ 支持 | ✅ 支持 |
| 维护风险 | 最低 | 低 | 中 | **高**（版本分叉） |

- **A** 已经在 `fnos/easytier/`，真机装过 🖥，随时能发。它的交付物里没有 LightTier 的一行代码。
- **F2** = 保留 A 的两个容器不动，把打开的界面从官方控制台换成自研前端。可行性来自两个上游事实：`easytier-web` 的默认编译**不带 embed 前端**（前端是独立 Vite 工程，embed 只是 feature 开关），而官方发布了 **`easytier-frontend-lib`**——一个带 `codegen:proto` 的 protobuf-ts 客户端库，即 web 后端 API 契约有现成 TS 客户端可 import，不用逆向。
- **B+** = 一个容器里跑 Node agent，由 agent 生成 TOML、spawn/kill core 子进程、跑 `easytier-cli --output json` 读状态。这是"把 LightTier 桌面版搬到服务器"的直译，复用现有前端与抽象层，但要自己承担内核编排。
- **F1** 技术上成立但性价比最差：F2 能拿到的观感它都能拿到，却额外持有一个上游分叉，每次跟版本都要重跑一遍跨版本核对。

**F1 基本可以从候选里划掉。** 真正的选择只在 A / F2 / B+ 三者之间。

---

## F2 为什么便宜

1. 特权问题已经用官方文档化的方式解决了——A 的 compose 里 `cap_add: NET_ADMIN` + 挂载 `/dev/net/tun` 已经真机跑通过 🖥，F2 沿用同一套。
2. 账号体系、ACL、成员管理、配置热下发、数据库迁移，全部由官方 web 后端承担，**一行不用写**。
3. 前端工作量集中在"界面"本身，API 层是 `easytier-frontend-lib` 直接 import。
4. 唯一必须自己加的是**一层同源反代**：自研静态站点和 API 不同源会撞 CORS，反代同时把这个解决了。

## B+ 为什么仍然值得存在

1. 它是唯一能让 NAS 复用**桌面版同一份前端**的方案（项目已把内核操作收敛到 `coreApi.ts` + `useMockData.ts` 两个分发点，加第三档 `fnos` 分支即可，视图层不动）。
2. 配置形态是 LightTier 原生的 TOML，桌面已有的配置文件可以直接搬到 NAS，不需要转换成"中心网络成员"模型。
3. 不依赖 web 控制台的账号体系（LightTier 本地应用本来就没有 session）。

代价：内核启停、端口分配、冲突检测、状态轮询这些原来由 Tauri 壳干的活，都要在 agent 里重写并长期维护。

---

## 开工前必须打钩的一件事

❓ **控制台里给同一台设备建的"第 N 个网络"，转发到底跑在哪个进程里。**

源码里存在**两个不同的 `NetworkInstanceManager`**：core 侧（LightTier Android 路径用的 `easytier::instance_manager::...`）和 web 服务端侧（`crate::central_network::gateway::...`）。而 web 那个的注释显示 **Gateway 是服务端进程内的设施**——如果 NAS 上的第 N 个网络是由 web 进程承载而非 core，那"关掉控制台这些网络还在不在"就会和直觉不符，这对 F2 的体验设计有直接影响。

这个只能真机定案，方法很轻（详细版第十一节有完整步骤）。**它不阻塞 A，但阻塞 F2 的界面语义设计。**

---

## 建议的顺序

1. 发 A（零成本），同时用这次真机安装把上面那条 ❓ 和 `/dev/net/tun` 的可用性一起打钩。
2. 默认主力做 **F2**——它把"LightTier 观感"这件事的成本压到只花在前端。
3. 只有在第 2 步做完、确认"两套界面的维护成本"真的痛，才回头做 **B+** 统一代码。

这个顺序的好处是：F2 的产出物（一套自研前端）即使将来转 B+ 也不浪费，而 B+ 的 agent 一旦不做就是纯沉没成本。
